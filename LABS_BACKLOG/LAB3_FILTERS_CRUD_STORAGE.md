# ЛР3 - UI фильтрации, управление данными и объектное хранилище

## Цель

Расширить MVP фильтрацией/поиском/сортировкой/пагинацией, усилить CRUD-потоки и безопасную работу с файлами в объектном хранилище.

## Зависимости

- Требует ЛР1 (RBAC) и ЛР2 (токенная auth).
- Все новые операции обязаны учитывать права доступа.

## Границы лабораторной

- Делать: фильтры, CRUD UX, валидации, ошибки, файловые ограничения, безопасная выдача файлов.
- Не делать: SEO и сторонние API (это ЛР4), полный тест-контур (это ЛР5).

## Бэклог задач (выполнять по порядку)

1. **Аудит сущностей и сценариев**
  - определить, где нужны фильтры (например: локации, этажи, лидерборд/результаты, пользователи);
  - зафиксировать минимум 3 параметра фильтра для каждой целевой страницы.
2. **Backend API для фильтрации**
  - query params: `search`, `sortBy`, `sortDir`, `page`, `pageSize`, предметные фильтры;
  - валидация входных параметров;
  - унифицированный ответ: `items`, `total`, `page`, `pageSize`.
3. **Frontend фильтры и состояние**
  - формы фильтров + поиск + сортировка + пагинация;
  - сохранение состояния в query params;
  - корректный UX при пустой выдаче и ошибках.
4. **CRUD-операции и валидация**
  - create/edit/view/delete для выбранных сущностей;
  - серверная валидация обязательных полей;
  - клиентская валидация до отправки;
  - обработка `400/403/404/409`.
5. **Безопасность файлов в object storage**
  - ограничить MIME-типы и максимальный размер;
  - добавить безопасную выдачу файлов (предпочтительно pre-signed URL);
  - удаление файла + очистка метаданных в БД;
  - отказоустойчивость при частичных сбоях.
6. **RBAC-согласованность**
  - все CRUD и файловые операции проверяются через permissions;
  - пользователь видит только разрешенные действия.

## Критерии готовности (DoD)

- Работают фильтры, поиск, сортировка, пагинация на целевых страницах.
- Состояние фильтров сохраняется при навигации.
- CRUD операции корректно валидируются на клиенте и сервере.
- Файлы загружаются/получаются/удаляются безопасно и предсказуемо.
- Роли и права из ЛР1-ЛР2 соблюдаются на всех новых потоках.
- Игровые режимы и лидерборд не сломаны.

## Инструкции для Cursor

1. Сначала стандартизируй backend-контракты фильтров.
2. Затем внедряй frontend-фильтры поверх стабильного контракта.
3. Отдельным шагом усили файловую безопасность.
4. После каждой крупной правки выполняй smoke:
  - создание/редактирование/удаление сущностей;
  - upload/download/delete файлов;
  - обычный игровой проход.

## Промпты для Cursor

### Prompt A - Проектирование фильтров

```text
Проанализируй сущности приложения и предложи единый контракт фильтрации:
search, сортировка, пагинация, предметные фильтры.
Для каждого endpoint укажи входные параметры, валидацию и формат ответа.
```

### Prompt B - Backend фильтрация и CRUD

```text
Реализуй на backend фильтрацию/поиск/сортировку/пагинацию для выбранных сущностей.
Добавь валидацию query/body и единый формат ошибок.
Проверь совместимость с RBAC из ЛР1-ЛР2.
```

### Prompt C - Frontend UI фильтров

```text
Добавь на frontend:
1) форму фильтров (>=3 параметров),
2) поиск,
3) сортировку,
4) пагинацию,
5) сохранение состояния через query params.
Обработай loading/empty/error состояния.
```

### Prompt D - Object storage hardening

```text
Усиль работу с файлами:
1) whitelist MIME и limit размера;
2) безопасная выдача файлов (pre-signed URL или эквивалент);
3) удаление файла и метаданных;
4) обработка ошибок object storage без падения бизнес-логики.
```

4. Схема работы с объектным хранилищем и меры безопасности.
